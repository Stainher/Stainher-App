# Auditoría técnica y funcional Stainher App V15.24

Fecha: 01-09-2026  
Base revisada: ruta pública `v1524r4` y aplicación `v1524r2`

## Resumen ejecutivo

La aplicación mantiene los flujos operativos, pero la base histórica continúa concentrada en un `index.html` de aproximadamente 1,6 MB, 11.619 líneas, 43 bloques JavaScript y 40 bloques de estilos. Sobre esa base se cargan módulos V15.24 adicionales. La arquitectura funciona por prevalencia de la última definición y por envolventes sucesivas; por ello, el orden de carga es todavía una dependencia crítica.

No se recomienda eliminar en bloque los archivos denominados `hotfix`: la inspección demuestra que aún aportan comportamientos vigentes en Turnos e Informes. Se clasifican como deuda técnica activa y deben consolidarse gradualmente con pruebas de equivalencia.

## Hallazgos

| Prioridad | Hallazgo | Riesgo | Acción aplicada |
|---|---|---|---|
| Alta | Varias definiciones históricas de renderizadores críticos | Una carga incompleta puede reactivar una versión anterior | Cargador autoritativo con estado, error explícito y orden estable |
| Alta | Descarga secuencial de módulos | Mayor tiempo de inicio, especialmente en móvil | Precarga paralela conservando ejecución secuencial |
| Alta | Parches aún vigentes marcados como “pendientes” o “candidate” | Confusión sobre qué código está publicado | Clasificados; no eliminados sin equivalencia funcional |
| Media | Modales sin semántica uniforme ni cierre por teclado | Experiencia desigual y accesibilidad limitada | Capa UX transversal para foco, Escape y atributos de diálogo |
| Media | Navegación sin estado accesible uniforme | Menor claridad para tecnologías de asistencia | `aria-current`, etiquetas y título contextual por página/rol |
| Media | Animaciones sin respetar preferencia de movimiento reducido | Molestia o dificultad para algunos usuarios | Regla global `prefers-reduced-motion` |
| Media | Botones móviles pequeños o acciones comprimidas | Errores táctiles | Altura táctil mínima y acciones principales a ancho completo |
| Baja | Comentarios y nombres de versiones heredados | Dificulta mantenimiento | Documentado para consolidación posterior |

- `hotfix2`: habilita la edición directa del día seleccionado; activo.
- `hotfix3`: consolida glosa y colores de novedades; activo.

## Ruta segura de refactorización posterior

1. Extraer cada dominio desde el HTML histórico sin modificar su API global.
2. Crear pruebas de equivalencia por rol y por flujo antes de retirar cada definición antigua.
3. Integrar los cuatro hotfix de Turnos en un único módulo autoritativo.
4. Integrar estilos repetidos por módulo y retirar únicamente reglas demostrablemente inaccesibles.
5. Reducir progresivamente el `index.html` hasta dejar estructura, dependencias y punto de arranque.

La refactorización completa no debe hacerse como una sustitución única: el flujo de tres firmas, permisos personalizados, malla 7×7, informes y correo requieren validación individual antes de retirar las capas anteriores.
